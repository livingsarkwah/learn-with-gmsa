## Plan: Shared Stale Resource Cache

Use TanStack Query for shared server-state caching and stale-while-revalidate behavior. Users will see cached data immediately, while fresh data loads in the background. Also optimize the resource query itself, since it currently performs many per-resource relation and signed-URL requests.

**Steps**
1. Add TanStack Query and configure a shared `QueryClient` with:
   - 2-5 minute `staleTime`
   - Request deduplication
   - Retry/backoff
   - Refetch on focus/reconnect
   - Cached data retained during refresh

2. Add shared query hooks for:
   - Published resources
   - Admin resources
   - Individual resources
   - Courses, programs, colleges, categories, collections
   - Counts

3. Migrate Home, Library, Search, Admin Resources, Dashboard, Analytics, and realtime analytics to those hooks.

4. Update loading states:
   - Show skeleton/loading UI only when no cached data exists.
   - Keep stale data visible during background refresh.
   - Show a small “updating” indicator while `isFetching` is true.
   - Preserve cached data when a refresh fails.

5. Optimize `resources.ts`. The current `mapRows` function can trigger several relation queries per resource. Replace that with:
   - One joined Supabase query, if generated types support it, or
   - Bulk relation fetches followed by in-memory ID mapping.

6. Invalidate relevant query keys after admin mutations and download-count updates.

7. Connect Supabase realtime events to query invalidation, with event coalescing/debouncing so bursts do not trigger repeated fetches.

8. Optionally persist safe public/catalog data to `localStorage`. Do not persist admin data or long-lived signed URLs.

**Relevant files**

- `package.json` — add TanStack Query dependencies.
- `App.tsx` — add the query provider.
- `src/lib/queryClient.ts` — central query configuration.
- `hooks` or `src/lib/queries` — shared query hooks and query keys.
- `resources.ts` — remove the N+1 relation-fetch pattern.
- `HomePage.tsx` — shared published-resource query.
- `LibraryPage.tsx` — cached resource display.
- `SearchPage.tsx` — reuse the resource cache.
- `ResourcesPage.tsx` — mutation invalidation.
- `useRealtimeAnalytics.ts` — shared admin query and realtime invalidation.
- `DashboardPage.tsx` and `AnalyticsPage.tsx` — shared analytics data.
- `useDataCounts.ts` — cached count queries.
- `README.md` — document caching and freshness behavior.

**Verification**

1. Run `pnpm build`.
2. Navigate Home -> Library -> Search and confirm only one shared resource request occurs.
3. Revisit pages within the freshness window and confirm cached data appears immediately.
4. Throttle the network and confirm stale data remains visible during refresh.
5. Verify refresh errors retain the previous successful data.
6. Create, update, and delete an admin resource, then confirm Dashboard, Analytics, and Resources update without a full reload.
7. Compare Supabase request counts before and after the relation-loading optimization.

**Decisions**

- Use TanStack Query instead of `useMemo`; `useMemo` only optimizes local calculations and does not cache server data.
- Use approximately 2-5 minutes of staleness initially.
- Avoid fake placeholder records.
- Keep Supabase and the existing demo-data fallback.
- Exclude broad UI redesign and server-side pagination/search changes from this work.
